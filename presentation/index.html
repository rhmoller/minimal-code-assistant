How Coding Agents Work

demystified, from scratch

How this was built

  1. Manual curl against a local model in LM Studio
  2. The same request as a fetch in TypeScript
  3. Wrap it in a loop → REPL
  4. Add tool calling → the model can do things
  5. Add skills → the model knows how to do things
  6. Add slash commands → /reset, /model, /dump, …

Each step is small. The whole thing is about 700 lines.

It's just HTTP

A coding agent is a while loop around a chat API call. That's it.

curl http://localhost:1234/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen/qwen3.6-35b-a3b",
    "messages": [
      { "role": "system", "content": "You are a helpful coding assistant." },
      { "role": "user",   "content": "What files are in the current directory?" }
    ]
  }'

Started with a curl like this against LM Studio. Everything else is built on top.

The response

{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": "I can help with that! Could you share your working directory?"
    },
    "finish_reason": "stop"
  }]
}

finish_reason: "stop" → model is done, show the reply
finish_reason: "tool_calls" → model wants to do something

Caveat: some OpenAI-compatible servers send "stop" even when the reply contains tool calls. Checking message.tool_calls?.length is the sturdier test.

A chat loop

Wrap the fetch in a loop and you have a REPL:

const messages: Message[] = [
  { role: "system", content: "You are a helpful coding assistant." },
];

while (true) {
  const input = await ask("> ");
  messages.push({ role: "user", content: input });

  const data = await callApi(messages);
  const reply = data.choices[0].message;

  messages.push(reply);           // keep the reply in history
  console.log(reply.content);     // show it to the user
}

No memory on the server. You send the whole conversation every time.

Messages are context

After a few turns, the array looks like this:

{ "role": "system", "content": "You are a helpful coding assistant." }, { "role": "user", "content": "What does the config file do?" }, { "role": "assistant", "content": "It maps model names to API endpoints and keys." }, { "role": "user", "content": "How is it loaded?" }, { "role": "assistant", "content": "With readFileSync('config.json') at startup." }, { "role": "user", "content": "Can it reload without restarting?" }, { "role": "assistant", "content": "Not currently — it's only read once on boot." }

Every request is stateless. "Memory" is just this array growing.
Context window = the most this array can hold. Past that, the request fails
or the server drops old messages. The model itself remembers nothing.

But this is just a chat client


The model can talk about your code.
It can't touch it.


To do real work it needs hands and eyes —
the ability to read files, run commands, search the codebase.


That's what tool calling is for.

Tool calling the contract

You describe your tools in JSON. The model decides when to call them.

// src/tools/bash.ts (simplified)
export const bash: Tool = {
  definition: {
    type: "function",
    function: {
      name: "bash",
      description: "Execute a bash command and return its stdout and stderr.",
      parameters: {
        type: "object",
        properties: {
          command: { type: "string", description: "The bash command to execute." },
        },
        required: ["command"],
      },
    },
  },
  async execute(args) {
    const { stdout, stderr } = await execAsync(args.command);
    return (stdout + stderr).trim();
  },
};

Tool calling what the model returns

Instead of text, the model returns a structured call:

{
  "choices": [{
    "message": {
      "role": "assistant",
      "tool_calls": [{
        "id": "call_abc123",
        "function": {
          "name": "bash",
          "arguments": "{ \"command\": \"ls -la\" }"
        }
      }]
    },
    "finish_reason": "tool_calls"
  }]
}

You execute it, append the result, and call the API again.

Needs a model trained for tool calling: qwen2.5-coder-7b just writes the call as text.

The agentic loop

user message
push to messages[]
→
API call
POST with full history
→
finish_reason?
tool_calls → execute, append results, call again ↺
stop → return reply to user

The loop in code

// src/index.ts (simplified)
async function chat(userMessage: string): Promise<string> {
  messages.push({ role: "user", content: userMessage });

  while (true) {
    const data = await callApi();
    const choice = data.choices[0];

    messages.push(choice.message); // always keep the full history

    if (choice.finish_reason !== "tool_calls") {
      return choice.message.content; // done
    }

    for (const toolCall of choice.message.tool_calls) {
      const args = JSON.parse(toolCall.function.arguments);
      const tool = toolMap.get(toolCall.function.name);
      const result = await tool.execute(args);
      messages.push({ role: "tool", tool_call_id: toolCall.id, content: result });
    }
    // loop: call API again with updated messages
  }
}

Tool calls in the history

Tool calls and their results are just more messages. The model sees the full trace.

{ "role": "user", "content": "rename all .js files to .ts" }, { "role": "assistant", "tool_calls": [{ "id": "call_abc", "function": { "name": "bash", "arguments": "{\"command\": \"ls *.js\"}" } }]}, { "role": "tool", "tool_call_id": "call_abc", "content": "file1.js\nfile2.js" }, { "role": "assistant", "tool_calls": [{ "id": "call_def", "function": { "name": "bash", "arguments": "{\"command\": \"mv file1.js file1.ts && mv file2.js file2.ts\"}" } }]}, { "role": "tool", "tool_call_id": "call_def", "content": "" }, { "role": "assistant", "content": "Done! Renamed file1.js and file2.js to .ts" }

Each tool result is fed back so the model can decide what to do next.

Skills 1/2

A skill is a folder with a SKILL.md and whatever supporting files it needs.

folder structure

.claude/skills/
└── commit/
    ├── SKILL.md
    ├── examples/
    │   └── good-commits.md
    └── scripts/
        └── lint-msg.sh

SKILL.md

---
name: commit
description: Create a git commit
  following conventional commits style
---

Always use conventional commits.
Run `git diff --staged` first.
See examples/ for good commit messages.
You can run scripts/lint-msg.sh to
validate the message before committing.

Reference docs, style guides, helper scripts — anything the model might need is co-located with the skill.

Skills 2/2 — progressive disclosure

Only a short catalog enters the system prompt at startup. The model pulls in what it needs, when it needs it.

at startup

<available_skills>
  <skill>
    <name>commit</name>
    <description>Create a git commit
      following conventional commits
    </description>
    <location>.../commit/SKILL.md
    </location>
  </skill>
</available_skills>

after activate_skill("commit")

<skill_content name="commit">
Always use conventional commits.
Run `git diff --staged` first.
...
<skill_resources>
  <file>examples/good-commits.md</file>
  <file>scripts/lint-msg.sh</file>
</skill_resources>
</skill_content>

What real agents add

The architecture is the same. The gap is everything around it.

  • Streaming — token-by-token output
  • Security — prompt injection, tool abuse
  • Sandboxing — isolating what tools can touch
  • Permission model — ask before destructive actions
  • Multi-modal — images, screenshots, PDFs
  • MCP — standard protocol for external tools
  • Sub-agents — spawning parallel workers
  • Long context management — compaction
